## Current public shape

`src/lib/index.ts` is the public barrel. It exports:

- primitives: `Text`, `Label`, `Icon`, `Divider`, `Surface`
- inputs, feedback, layout, navigation, and display components
- ambient and ornamental components
- patterns and full-page scenes
- registers/themes/grades, expressions, actions, motion, depth, and token helpers

The current API therefore already contains substantial expressive material: snippets, CSS custom properties, transforms, depth, canvas/ambient pieces, choreography, expressions, themes, and actions. The observed problem is not absence of visual capability alone. It is that the agent-facing and composition-facing abstractions still make finished scenes and conventional layout containers easier to select than relationships and art direction.

## Initial evidence and hypotheses

### Verified evidence

- `StageScene` uses a centered, theatrical structure with fixed label/heading/subheading/actions/ambient zones (`src/lib/components/scenes/StageScene.svelte:20-69`).
- `DepthScene` provides fixed ambient/ground/stage/foreground zones (`src/lib/components/scenes/DepthScene.svelte:25-78`).
- `Card` exposes `staggerOffset` as its only explicitly compositional prop while wrapping a fixed `Surface` card treatment (`src/lib/components/layout/Card.svelte:17-52`).
- `Grid` and `Stack` make conventional organization extremely direct (`src/lib/components/layout/Stack.svelte:17-58`, `Grid.svelte:15-120`).
- `Grid` is already context-aware about its own width through `ResizeObserver`; this is a narrow, inspectable adaptation rather than a global layout engine.
- The scenes API documentation says scenes are “full-page layout templates” and that “one scene per page is the expected pattern” (`docs/api/scenes.md:1-4`).
- `SKILL.md` and `INSTALL.md` contain historical `data-register`/`applyRegister` references even though the implemented helpers use `data-weight`/`applyWeight` (`src/lib/system/register.ts:1-85`).
- `COMPONENTS.md` contains valuable component usage guidance but mostly describes components as the correct answer to a task, not as materials with compatible visual roles and relationships.

### Hypotheses to test, not decisions

1. Fixed scene slots and “use this before building” guidance may be stronger causes of structural repetition than the absence of visual effects.
2. Existing snippets, `as`, class/CSS seams, depth, and actions may already be enough material for diverse compositions if the agent receives a relationship vocabulary and anti-template prompts.
3. A small typed composition graph with explicit hard/soft precedence may provide more expressive leverage than adding props to every existing component.
4. Most contextual adaptation can likely be static or author-declared; live runtime geometry should be limited to cases that cannot be derived before render.
